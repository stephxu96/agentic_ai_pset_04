# AI Enters the CAD-to-Simulation Handoff

**What changed, and which developments matter most to engineering teams?** AI is moving into discrete handoffs inside engineering workflows: reusable CAD-feature creation and simulation setup. That is more consequential than a generic chat interface beside CAD, but the available evidence supports workflow announcements—not dependable production geometry or valid engineering decisions.

*As of October 16, 2026.*

Watch the video version: https://www.youtube.com/watch?v=pICJnOCUzMc

Onshape says its FeatureScript MCP Server connects large language models to Onshape so teams can generate custom features from natural-language requests. [01-c1] It also says this text-to-code-to-CAD workflow can carry requirements from an LLM request into Onshape, including model-based-definition annotations. [01-c2]

The important distinction is that FeatureScript is code for reusable parametric CAD functionality, rather than a one-off geometry prompt. A team could ask for a standards-oriented feature, inspect the generated script, exercise its parameters, and determine whether it implements the intended design rules. That makes the proposal useful as a workflow direction: it puts an LLM upstream of artifacts that engineers can review and reuse.

But the check does not match the larger capability some readers may infer. The evidence is Onshape’s product description, which establishes what Onshape says the server enables; it is not a disclosed test of generated FeatureScripts across requirements, edge cases, revisions, or manufacturing outcomes. Onshape’s statement therefore does not show that a generated feature preserves design intent in a production model. [01-c1] [01-c2]

The downstream announcement is more ambitious. Engineering.com reports that SimScale’s Engineering AI Agent is available through Onshape’s app store. [01-c3] SimScale says that, from one prompt, its agent can take a CAD model, propose a setup, mesh it, run physics, and return results in Onshape—even when geometry is not yet simulation-ready. [01-c4]

That places an agent at a different and riskier point in the chain. Generating a CAD feature asks whether the code and resulting geometry meet stated rules. Selecting a simulation setup asks whether the model answers the engineering question at all: loads, boundary conditions, material assumptions, contact definitions, mesh choices, solver settings, and result interpretation all matter. A completed run is not evidence of a valid analysis.

Here, too, the observed check is narrower than the claim. Engineering.com’s report supports the reported availability of the integration. [01-c3] The quoted SimScale release supports what SimScale says the agent can do in its described workflow. [01-c4] Neither source presents a public comparison of the agent’s proposed setups with engineer-reviewed ground truth, nor a validation study showing that its results match the relevant physical system. Those are the checks that would match a claim about correct simulation decisions.

Taken together, the two announcements show more than either alone: AI is being attached to interfaces between engineering stages, not merely offered as an assistant that drafts text. [01-c7] My interpretation is that this changes how teams should evaluate adoption. For FeatureScript, review can center on code, parameter behavior, geometry, and encoded rules. For simulation, review must also center on the adequacy of the abstraction itself. The same “one prompt” interaction can conceal very different verification burdens.

Robotics supplies supporting context, not proof for either CAD workflow. In an NVIDIA Robotics Office Hour, a presenter states that Newton physics for robot simulation is completely open source. [01-c5] The check is the presenter’s statement in NVIDIA’s video, which supports only NVIDIA’s claim about Newton’s availability and contribution model. It does not demonstrate simulator accuracy, transfer to hardware, or usefulness for a particular CAD-to-simulation workflow.

A Physical AI Podcast episode describes a blind hardware evaluation: 10 manipulation tasks, three attempts per task, a shared time window, and a shared scoring sheet. [01-c6] If verified, that protocol is closer to the kind of explicit evaluation discipline engineering agents need: common tasks, bounded attempts, and a shared scoring procedure. But the available evidence is an automatic transcript of a podcast passage, not the underlying evaluation materials or an independently auditable grader. Its figures and protocol details remain uncertain until checked against the audio, video, and original evaluation documentation. [01-c6]

The limitation is straightforward. Onshape and SimScale are commercial claimants, and the evidence does not independently validate their claimed outcomes. NVIDIA’s presentation is likewise a source claim, while the podcast is a report of someone else’s protocol. None establishes that AI-generated CAD functions are production-safe or that agent-selected simulation setups are correct.

Teams should pilot these tools where inputs are constrained and engineering review remains explicit. For CAD, require tests tied to intended rules and reusable parameters. For simulation, require reviewers to approve setup assumptions before treating outputs as decisions. Watch next for public task suites, disclosed graders, repeatable comparisons with engineer-authored setups, and evidence that ties a completed simulation to physical validation.
